# Локальный запуск Private Gateway Web

Это отдельное веб-приложение. Оно не меняет VPN-сервер, маршруты, DNS, брандмауэр
или установленный Private Gateway Client. Встроенный клиент на главной остается
демонстрацией. Docker-конфигурация ниже слушает только `127.0.0.1`.

## Запуск в Docker

Нужны Docker с Compose v2, Python 3 и bash. На Windows команды выполняются в Git Bash,
на macOS и Linux — в терминале. Все команды запускаются из корня репозитория.

1. Запустите `deploy/local.sh up`.
   Скрипт создаст `.env.local` со случайными ключами и паролем новой локальной базы,
   соберет API и интерфейс, дождется PostgreSQL, применит миграции отдельной командой
   и запустит приложение. При повторном запуске файл настроек и база сохраняются.
2. Создайте первого администратора: `deploy/local.sh admin --email admin@example.com`.
   Замените адрес своим. Пароль вводится в терминале без отображения и без аргумента
   командной строки. Готовых пользователей и общих паролей в приложении нет.
3. Откройте **http://127.0.0.1:8080**. Войдите с указанными email и паролем, добавьте
   ключ в приложение-аутентификатор, подтвердите код и сохраните резервные коды.
4. В разделе администрирования создайте приглашение для нужного email. Для действия
   нужен текущий код 2FA администратора. Передайте одноразовый код приглашения
   адресату своим обычным способом; сайт не отправляет письма самостоятельно.

Остановка — `deploy/local.sh down`. Эта команда сохраняет том базы и скачиваемые файлы.
Состояние — `deploy/local.sh status`, журнал API — `deploy/local.sh logs api`.
При конфликте порта 8080 остановите другой локальный процесс или согласованно измените
порт Caddy и `PGWEB_PUBLIC_ORIGIN`; cookie/CSRF привязаны к точному origin.

## Конфигурация и хранение

`.env.example` — шаблон без рабочих секретов. `.env.local` создается с правами `0600`
на системах, где доступны Unix-права. На Windows ограничьте доступ ACL своего профиля.
Файл не исполняется как shell-скрипт и не попадает в Git или Docker build context.
Существующий файл `init` никогда не перезаписывает.

| Настройка | Назначение |
| --- | --- |
| `POSTGRES_PASSWORD` | Пароль только новой локальной базы в Docker |
| `PGWEB_DATABASE_URL` | PostgreSQL через asyncpg; для запуска Python на компьютере |
| `PGWEB_SECRET_KEY` | 32 случайных байта в hex для HMAC токенов |
| `PGWEB_MASTER_KEYS` | Отдельные ключи шифрования TOTP: `версия:64hex`, несколько через запятую |
| `PGWEB_PUBLIC_ORIGIN` | Точный адрес браузера; Compose задает `http://127.0.0.1:8080` |
| `PGWEB_COOKIE_SECURE` | Только для локального HTTP: `false`; будущий HTTPS требует `true` |
| `PGWEB_DOWNLOAD_ROOT` | Закрытая директория файлов; в Compose `/downloads` |

API работает от пользователя `10001`, файловая система контейнера доступна только
для чтения. PostgreSQL доступен только во внутренней сети Docker. Caddy перезаписывает
`X-Forwarded-For`; API доверяет прокси только в выделенной сети `172.31.247.0/28`.
При конфликте с другой локальной сетью менять подсеть и доверенный диапазон нужно вместе.
Redis не запускается: очередей фоновых задач в текущем составе нет.

Миграции не спрятаны в старте API. Отдельная команда — `deploy/local.sh migrate`.
Перед будущей миграцией рабочей базы потребуется ее резервная копия; локальный стенд
не является настройкой резервного копирования production.

## Файлы клиента

До добавления проверенных выпусков каталог показывает все пять платформ как
недоступные. Реальные номера версий и ссылки не генерируются.
В Docker файлы хранятся в отдельном томе `releases`, подключенном к API только для
чтения и вообще не подключенном к Caddy. Скачивание идет через API с повторной
проверкой сеанса и отзыва доступа. Внесение нового файла выполняет короткоживущий
контейнер CLI с правом записи в этот том. Положите проверенный выпуск в
`.localdata/imports` и вызовите `deploy/local.sh cli publish-release --platform windows
--version ВЕРСИЯ --file /imports/ИМЯ_ФАЙЛА` (одна команда). Подставьте настоящие
платформу, версию и имя файла. CLI сам копирует файл, считает SHA-256 и записывает
метаданные; исходный файл в imports не изменяется. Входной файл должен быть читаем
пользователем контейнера `10001`.

Для iOS используется `deploy/local.sh cli set-ios --version ВЕРСИЯ --url URL_APP_STORE`
только после появления настоящего приложения. Скрыть выпуск —
`deploy/local.sh cli disable-release --platform ПЛАТФОРМА`. Остальные команды:
`deploy/local.sh cli --help`. В режиме Python без контейнера каталог хранения —
`.localdata/downloads`; контейнерные и нативные хранилища не смешиваются.

## Разработка без сборки образа

Это режим для изменения исходников: Python 3.12+, Node.js 24 и Docker для локальной БД.

```bash
scripts/cloud-setup.sh
scripts/dev.sh init
scripts/dev.sh db
scripts/dev.sh migrate
scripts/dev.sh admin --email admin@example.com
scripts/dev.sh start
```

Интерфейс доступен на **http://127.0.0.1:5173**, API — на `127.0.0.1:8000`.
Vite пересылает `/api` в API с тем же origin. Порт PostgreSQL `127.0.0.1:5433`
открывает только файл `compose.dev.yml`. `Ctrl+C` останавливает процессы этого запуска;
`scripts/dev.sh stop-db` останавливает локальную БД без удаления данных.
Запуск API отдельно не применяет миграции автоматически.

`scripts/cloud-setup.sh` устанавливает зависимости в `backend/.venv` и
`frontend/node_modules` по lock-файлам с проверкой хешей. Системные службы и VPN он
не устанавливает. В managed cloud Docker-сборка получает CA через временный BuildKit
mount, когда задан `CODEX_PROXY_CERT`; сертификат сессии не встраивается в образы.

## Проверки

`scripts/check.sh` выполняет Ruff, тесты backend, TypeScript, тесты frontend и сборку
Vite. Перед запуском задайте `PGWEB_TEST_DATABASE_URL` через окружение процесса для
**отдельной** PostgreSQL-базы с `test` в имени. Тесты пересоздают ее таблицы, поэтому
рабочую базу им передавать нельзя. Секреты тестов генерируются самим процессом.
Результат backend сохраняется в `artifacts/test-results/backend.xml`.

`deploy/local.sh config` проверяет Compose, не печатая разрешенные значения секретов.
После запуска контейнеров `python3 deploy/smoke.py` проверяет готовность API, страницу,
правила встраивания клиента, CSRF и отказ в скачивании без входа. CI повторяет проверки
на Linux, проверяет миграцию в PostgreSQL 18, собирает оба образа и сканирует репозиторий
gitleaks. Публикации сайта и workflow разворачивания нет.
Браузерный прогон `tests/browser-smoke.cjs` в CI выполняется через готовый Caddy
на пяти ширинах и двух языках, включая переход к входу без сеанса.

Базовые образы закреплены digest, зависимости Python — версиями и хешами,
зависимости Node — `package-lock.json`, действия CI — SHA. Обновлять их нужно вместе
с повторным прогоном проверок. Источники подхода и отличия от AI Agent Capper:
[infra-reuse.md](sources/infra-reuse.md).

## Перед отдельным этапом размещения

Нужны отдельный хост для сайта, согласованный домен, HTTPS Caddy, закрытый PostgreSQL,
новые рабочие ключи вне Git, резервное копирование базы и ключей с проверкой
восстановления и проверенные файлы выпусков. Порты, домен, файлы и учетные записи
работающего VPN-сервера для этого не используются. Данный этап их не настраивает.
