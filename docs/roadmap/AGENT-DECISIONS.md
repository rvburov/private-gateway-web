# Решения при разработке

| № | Решение | Альтернативы и основание |
| --- | --- | --- |
| 001 | Сохранить `mockup/` как согласованный эталон, приложение строить в `frontend/` и `backend/` | Замена макета лишила бы проект проверенного визуального источника. |
| 002 | Адаптировать AGENTS.md клиента под веб-стек | Команды .NET, TUN, firewall и тесты служб неприменимы к сайту. Облачная работа остается в собственной копии. |
| 003 | Не подключать Redis на первом этапе; хранить состояние доступа в PostgreSQL | У сайта нет очередей AI-задач Capper. Лимиты и одноразовые операции должны быть атомарны в общей БД. |
| 004 | Каталог выпусков изначально пуст; приватная выдача подключенных файлов через API | Нет утвержденных версий клиента и App Store URL. Публичные пути обходили бы отзыв доступа. |
| 005 | Проверять доступные версии пакетов и закреплять lock-файлами | Версии в исходном Capper служат ориентиром, но сборка должна использовать реально доступные пакеты. |
| 006 | Основные пакеты закреплены в тех же версиях, что в Capper | Проверка реестров подтвердила доступность версий. Универсальные Python lock-файлы сохраняют условия Windows для colorama и uvloop. |
| 007 | Caddy перезаписывает адрес клиента, API доверяет только выделенной сети прокси | Иначе один IP прокси объединяет лимиты всех посетителей; доверие любому внешнему X-Forwarded-For позволяет обходить их. |
| 008 | Подключение выпусков — отдельная CLI-команда, API читает хранилище без права записи | Реальных файлов еще нет. Управление каталогом в веб-админке расширило бы согласованный состав и поверхность загрузки файлов. |
| 009 | Проверка CI для веб-приложения на Linux и браузерных размерах | Трехплатформенные тесты VPN-служб из AGENTS.md клиента здесь неприменимы. Нативные Windows/macOS запуски не выдаются за проверенные. |
| 010 | «Спектр» оформлен токенами в `style.css` и отдельным `spectrum.css`, одинаковым в `mockup/` и `frontend/src/styles/` | Палитра остается в одном месте, правила оформления не смешиваются с разметкой v8. Варианты A и B остались только в черновике и в код не вошли. |
| 011 | Цвет платформы задается атрибутом `data-platform`, а не порядком карточек | Порядок карточек может измениться; цвет Windows, macOS, iOS, Linux и Android не должен зависеть от позиции. |
| 012 | На телефоне колонка иконки в карточке загрузки расширена до 44 px под плитку 44 × 44 | Плитка 52 px в колонке 37 px наезжала на заголовок платформы. |
| 013 | В `tests/browser-access.cjs` кнопки загрузки считаются после появления сетки | Заголовок кабинета показывается до ответа `/api/downloads`; без ожидания проверка зависела от скорости ответа. |
| 014 | Один `deploy/Caddyfile` для стенда и сервера; IP посетителя — `{client_ip}` при доверии только `PGWEB_TRUSTED_PROXIES` | На сервере доверяется подсеть `caddy-ingress`, локально — только loopback контейнера. Подмена `X-Forwarded-For` не меняет адрес для лимитов ни там, ни там. |
| 015 | HSTS, удаление `Server` и `Via` — в файле сайта для Caddy capper, который пишет `deploy.sh` | TLS завершает Caddy capper; HSTS имеет смысл только на HTTPS-входе. |
| 016 | `deploy.sh` проверяет новый файл сайта вместе со всей конфигурацией Caddy capper в отдельном контейнере его образа и только потом делает `caddy reload` | Ошибка в файле сайта не должна остановить или сломать capper; при неудаче возвращается прежний файл. |
| 017 | Подсеть `caddy-ingress` `deploy.sh` берет из `docker network inspect`, а не из настроек | Если capper изменит подсеть, доверие сайта не разойдется с ней молча. |
| 018 | `server-setup.sh` переносит ключи age и S3 из `deploy/.env` capper, папка в бакете — `private-gateway-web` | Решение владельца: тот же ключ и бакет. Значения не выводятся; capper удаляет старые копии только в своей папке (проверено по его `common.sh`). |
| 019 | Бэкапы в 01:45 и проверка восстановления в 02:45 UTC | Сдвиг на 15 минут от capper, чтобы два `pg_dump` и выгрузки не шли одновременно. |
| 020 | Файлы выпусков не входят в бэкап | Это проверенные сборки владельца, у него остаются исходники; на новом сервере их вносят заново через CLI. Метаданные — в базе. |
| 021 | `/api/health` отвечает версией коммита (`PGWEB_VERSION` из сборки) | `deploy.sh` проверяет, что через вход отвечает именно новая версия, как у capper. |
| 022 | IP сервера не пишется в публичный репозиторий; домен сайта — пишется | Домен — публичный адрес сайта; адрес и настройки сервера остаются в `deploy/.env` на сервере и в выводе `server-setup.sh`. |
| 023 | Задача CI «Рабочий стек за общим входом» с имитацией Caddy capper (`tests/deploy/front`) | В облачной среде агента сборка за прокси не повторяет сервер; CI на Ubuntu 24.04 проверяет `server-setup.sh` и `deploy.sh` целиком. |
| 024 | Выпуск передается на сервер по SSH в stdin, команда принудительная (`import-release.sh --ssh`, `restrict`), SHA-256 — аргументом | Токен GitHub на сервере не нужен; ключ клиента не может ни деплоить, ни читать данные; поврежденный при передаче файл не вносится. |
| 025 | На сайт — один файл на платформу: `.msi`, `.dmg`, `.deb`, `.apk`; бета не публикуется | В каталоге сайта по слоту на платформу; установщики, а не архивы, — то, что советует страница выпуска клиента. `.rpm` и архивы остаются на GitHub. |
| 026 | Workflow клиента запускается по `workflow_run` «Выпуск на GitHub», а не по событию release | Выпуск создается токеном `GITHUB_TOKEN`, а его события другие workflow не запускают. |
| 027 | Аккаунт приложения — тот же аккаунт сайта, вход паролем и кодом 2FA одним запросом | Пользователь сказал «делай все» без выбора; один аккаунт проще и уже защищен 2FA. Без настроенной 2FA вход в приложение запрещен (`setup_required`). |
| 028 | За доступом приложение ходит на сайт, не в Private Gateway | Правило проекта: VPN-сервер и профили не меняются. Сайт выдает токен устройства и отвечает «доступ есть/нет». |
| 029 | Устройство — установка приложения (`uid`), токен только хешем, продление при проверке на 30 дней | Повторный вход того же устройства не тратит место; без проверок токен гаснет сам. |
| 030 | Сверх лимита устройств вход отклоняется (`device_limit`), а не вытесняет старое устройство | Вытеснение позволило бы делить аккаунт по очереди. Место освобождает участник или администратор удалением устройства. |
| 031 | Сверх лимита входов на сайт завершается самый давний сеанс | Вход на сайт нужен самому участнику с нового устройства; отказ заблокировал бы его. Лимит 3 по умолчанию. |
| 032 | Лимит устройств: общий `PGWEB_DEVICE_LIMIT` и личный у участника (1..50), смена с кодом 2FA, без завершения сеансов | Основа будущих тарифов подписки без отдельной таблицы тарифов сейчас. |
| 033 | Завершение чужого входа или устройства администратором — без повторного кода 2FA, с записью в журнал | Действие только защищает участника и не повышает права. |
| 034 | В журналах и списках IP хранится без последних октетов (`/24`, `/48`), User-Agent — до 300 символов | Достаточно узнать сеть и устройство, лишние персональные данные не хранятся. |
| 035 | `/api/app/*` без CSRF, только `Authorization: Bearer` | Нативное приложение не имеет cookie сайта; без cookie подделка запроса из чужой страницы ничего не дает. Мутант «CSRF снят со всех путей» ловит тест. |
| 036 | Защиту кода от декомпиляции не делаем барьером: в клиенте нет секретов, решение о доступе на сервере | Любой код на устройстве пользователя распаковывается; обфускация только повышает трудозатраты. |
| 037 | «Запомненный» браузер привязан к своему последнему входу (`trusted_devices.session_id`); завершение входа вручную или вытеснением по лимиту гасит и его | Отзывать все доверенные браузеры участника; показать их отдельным списком; оставить как было. Разбор нашел обход: вход завершили, а браузер снова входит одним паролем. Привязка закрывает его и не заставляет вводить код на других своих браузерах |
| 038 | При отказе `device_limit` вход в приложение фиксирует израсходованный код 2FA или резервный код и пишет `app.device_limit` в журнал | Проверять лимит до кода; откатывать как раньше. Предъявленный одноразовый код не должен сработать второй раз; проверка лимита до кода раскрывала бы лимит без второго фактора |
| 039 | После верного пароля счетчики попыток входа очищаются и при отказах «нет 2FA» и «лимит устройств», как при входе на сайт | Не очищать. Иначе приложение, упершееся в лимит, закрывало участнику вход на сайт, где он и освобождает место |
| 040 | Отзыв сеанса, устройства и выход приложения сначала блокируют строку участника | Блокировать только сеанс или устройство. Один порядок блокировок со входом и отзывом доступа: без него запись журнала и отзыв доступа могли ждать друг друга (503) |
| 041 | На своей карточке администратор не меняет себе лимит устройств и видит текущий браузер отмеченным | Разрешить себе лимит. Сайт уже запрещает администратору менять себе роль и доступ; без отметки он мог завершить собственный вход |
